Data architecture: where we stand

An hourly batch pipeline on a medallion architecture. Connectors extract from three upstream APIs, load the raw payloads into a bronze zone and conformed records into silver, all in one Postgres warehouse. dbt (SQL) transformations inside the warehouse build the gold marts (topics, momentum scores) for the serving layer (API, website) and activation (email, Telegram). Built: sources → ingestion → bronze → silver → gold, plus orchestration. Not built: serving, activation, the production platform.

4 · Pipeline mechanics

The data engineering patterns the pipeline uses, how each is implemented, and the evidence.

Idempotency

Effectively-once loads

Jobs run at-least-once (retries, restarts). Every write is an upsert keyed on natural key + time bucket, so re-running a job in the same hour overwrites instead of duplicating.

Proven: tests re-run the same hour → no duplicates; 3 Wikipedia runs → still exactly 180 rows.

Incremental extraction

Sliding window + hot set

Discovery only asks for videos published in the last 24h. Snapshots only refresh the "hot set" (videos under 7 days old). Older items stop costing quota.

Live: 97 videos discovered for 200 units; snapshot of all 97 = 2 units.

Late-arriving data

Lookback window (rolling backfill)

Wikipedia publishes a day's counts about a day late and may revise them. Each run re-fetches the last 30 days, and the upsert overwrites any late corrections.

Live: 6 articles × 30 days backfilled on the first run.

Schema contracts

Validate at the edge

pydantic models declare only the fields we use. If an API renames or drops one, validation fails, the run is marked error, and nothing half-parsed reaches silver.

Tested: missing-data paths (404 article, missing category, hidden subscriber counts). Gap: no test yet for a malformed response.

Fault tolerance

Retry with exponential backoff

429, 5xx and network errors retry up to 5 times (2s, 4s, 8s… capped at 60s). Other 4xx (bad key, bad request) fail fast because retrying won't help.

Proven today: the 16:05 snapshot retried through the Mac going to sleep and finished with complete data.

Cost control

Quota budget, pessimistic accounting

Each YouTube call is charged to the run before it's made, retries included, and committed immediately. Jobs stop at 9,000 of 10,000 units (resets at midnight Pacific).

Live: 208 units used; today's retries were charged (6 instead of 2).

Concurrency control

One run per job, missed runs collapse

max_instances=1 means a slow run is never overlapped by the next. coalesce means 5 missed runs become 1. Runs over 10 minutes late are skipped rather than piling up.

Live: today's runs fired 6m45s late, within the grace period, and weren't duplicated.

Upstream dependency

Sensor-style wait

If an upstream resource doesn't exist yet (the Twitch category), the run records waiting, not error, and re-checks every hour. It starts producing data automatically.

Live: 2 Twitch runs, status waiting, 0 false alarms.

Event time vs processing time

Bucketed snapshot time

captured_at is the hour bucket, not the exact fetch time (that lives in bronze). Rates will be normalised per hour in P3.1; this assumes snapshots land about 60 minutes apart.

Limitation seen today: the 15:00 and 16:00 readings were actually 33 minutes apart (a manual run, then a sleep-delayed run).

10 · Architecture rules we build to

Every new piece follows these.

Bronze is append-onlyNever updated, purged after 30 days.
Every table declares its grainWritten in the model docstring and on this page.
Loads are idempotentUpsert on natural key + time bucket. Re-running anything is always safe.
Contracts at the edgeValidate every upstream response before it touches silver.
Gold derives only from silverAs dbt models, rebuilt each cycle. Manual fixes go in an overrides table, never into gold rows.
Every job writes a run recordStatus, rows, cost, error, in connector_runs.
Every dbt model has testsNo duplicates, no negative deltas, no null timestamps, at minimum.
DDL only via AlembicNo hand-edited schema. dbt views depend on items/signals: dropping or retyping their columns needs DROP SCHEMA analytics CASCADE first (the next dbt build recreates it).
Secrets never in URLs, logs or gitEnv vars now, Vault and GitHub secrets on the server.
Simplest tool that holdsEach has a written swap trigger (section 2).
