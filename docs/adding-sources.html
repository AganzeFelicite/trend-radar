Adding sources

A source is an upstream system that feeds the ingestion layer. Adding one means writing a connector that extracts on a schedule, validates every response against a contract, lands the raw payload in bronze, and upserts conformed rows into silver (items + signals), with tests. Once dbt is set up, you also add a dbt source with a freshness check and a staging model.

Plan (your call, Nov 4): get all sources in first, then build the transform layer with dbt. You can follow this page yourself in PyCharm, or tell me "add <source>" and I follow the same steps.

3 · Two ways to add data

Often you don't need a new connector at all.

A · Extend an existing source (config only)

Edit trend_radar/config.py, then docker compose up -d --build. No new code or tests.

trend_radar/config.py: more Wikipedia articles (free) 
WIKIPEDIA_ARTICLES = [
    "Grand_Theft_Auto_VI",
    # ...
    "Vice_City",          # exact title from the article URL, underscores for spaces
]
trend_radar/config.py: another YouTube search (costs quota) 
YOUTUBE_SEARCHES = [("GTA 6", "date"), ("GTA 6", "viewCount"), ("GTA VI", "date")]
YOUTUBE_SEARCH_EVERY_HOURS = 2   # 3 searches x 12 runs = 36/day, under the 60/day budget

Each search costs 100 units. The assert in config.py stops the worker from starting if you go over 60 searches/day (6,000 units).

B · New source (new connector)

For a new upstream system. Follow the 10 steps below. About 2–4 hours per source with tests.

  • 1 Python module + 1 test file
  • 3 lines of config, 1 env line, 1 compose line, 4 scheduler lines
  • 1 row in the docs
  • From P3.1: 1 dbt source entry + 1 staging model

4 · Adding a new source, step by step

The template is a generic JSON API called example: replace the name, URL and fields. The connector and tests below were run and pass (3/3, Nov 4).

1

Profile the source source assessment

Answer these before writing code. They decide the design.

QuestionWhy it matters
Is it an official API or feed?Official only, never scraping (brief rule)
Auth: none, key, OAuth or login session?Where the secret goes; whether a token needs caching and refresh
Limits: quota, rate limit, what errors look like?Schedule and budget. Some APIs return 200 with an error body (GDELT).
What is one record? (post, article, stream)The grain, which becomes item_type
Which numbers change over time?Those become signals. None → items only (derive counts in dbt)
How do we fetch only what's new?Incremental strategy: time window, cursor, or since-ID
Is history available? Are values revised later?Backfill and lookback window (like Wikipedia's 30 days)
Terms: storage limits, retention, commercial use, attribution?What we may store, for how long, and what the site must credit

Compose passes an unset variable as an empty string. For settings with a fallback, use os.environ.get("X") or "default", not get("X", "default").
3

Write the connector extract · contract · load

One file, trend_radar/connectors/example.py. Four parts, each matching a layer:

Contractpydantic models with only the fields you use. Schema drift fails the run.
Extract → bronze_get() with @retry_http, saves every body to raw_responses.
Conform → silverupsert_items / upsert_signals on a time bucket. Idempotent.
Run logconnector_run() records status, row count and error, whatever happens.
trend_radar/connectors/example.py 
"""Example: posts mentioning GTA 6, with like and reply counts. Hourly, API key."""

from datetime import datetime

import httpx
from pydantic import BaseModel
from sqlalchemy.orm import Session

from trend_radar import config
from trend_radar.connectors.common import retry_http, this_hour, upsert_items, upsert_signals
from trend_radar.db import RawResponse, connector_run

API = "https://api.example.com/v1/"
SOURCE = "example"  # lowercase; stored on every row and in connector_runs


# Contract: only the fields we use. If the API renames or drops one, validation fails the run loudly.
class _Post(BaseModel):
    id: str
    title: str
    url: str
    author_id: str
    author_name: str
    created_at: datetime
    likes: int
    replies: int


class SearchResponse(BaseModel):
    posts: list[_Post] = []
    cursor: str | None = None


def client() -> httpx.Client:
    # Secret in a header, never in the URL: httpx logs every request URL.
    return httpx.Client(base_url=API, headers={"Authorization": f"Bearer {config.EXAMPLE_API_KEY}"}, timeout=30)


@retry_http  # retries 429 / 5xx / network errors with backoff; other 4xx fail fast
def _get(s: Session, http: httpx.Client, endpoint: str, params: dict) -> dict:
    r = http.get(endpoint, params=params)
    r.raise_for_status()
    data = r.json()
    s.add(RawResponse(source=SOURCE, endpoint=endpoint, payload=data))  # bronze: exactly as received
    return data


def collect(http: httpx.Client | None = None) -> None:
    http = http or client()
    hour = this_hour()  # time bucket: a re-run in the same hour overwrites instead of duplicating
    with connector_run(SOURCE, "collect") as (s, run):
        params = {"q": config.EXAMPLE_QUERY, "limit": 100}
        for _ in range(config.EXAMPLE_MAX_PAGES):
            page = SearchResponse.model_validate(_get(s, http, "search", params))
            upsert_items(s, [
                dict(source=SOURCE, item_id=p.id, item_type="post", title=p.title, url=p.url,
                     channel_id=p.author_id, channel_title=p.author_name, published_at=p.created_at)
                for p in page.posts
            ])
            upsert_signals(s, [
                dict(source=SOURCE, item_id=p.id, metric_name=name, metric_value=value, captured_at=hour)
                for p in page.posts
                for name, value in (("likes", p.likes), ("replies", p.replies))
            ])
            run.items_count += len(page.posts)
            s.commit()  # commit per page: a crash on page 5 keeps pages 1-4
            if not page.cursor:
                break
            params["cursor"] = page.cursor

5

Test it contract + idempotency tests

A fake API via httpx.MockTransport against the real test database. Three tests minimum:

  • Data lands, and a re-run doesn't duplicate (idempotency)
  • The source's failure mode: bad key fails fast, no retries
  • Schema drift: a changed response fails the run and loads nothing
tests/test_example.py 
import httpx
import pytest
from pydantic import ValidationError
from sqlalchemy import func, select
from sqlalchemy.orm import Session

from trend_radar.connectors import example
from trend_radar.db import ConnectorRun, Item, Signal, engine


def fake_api(pages):
    """Serves `pages` in order and follows the cursor, like the real API."""
    seen = []

    def handler(req):
        seen.append(req)
        i = int(req.url.params.get("cursor", 0))
        more = i + 1 < len(pages)
        return httpx.Response(200, json={"posts": pages[i], "cursor": str(i + 1) if more else None})

    return httpx.Client(base_url=example.API, transport=httpx.MockTransport(handler)), seen


def post(i, likes=10):
    return {"id": f"p{i}", "title": f"GTA 6 post {i}", "url": f"https://example.com/p{i}",
            "author_id": "a1", "author_name": "Someone", "created_at": "2026-11-04T10:00:00Z",
            "likes": likes, "replies": 1}


def test_collect_follows_pages_and_rerun_is_idempotent():
    http, seen = fake_api([[post(1), post(2)], [post(3)]])

    example.collect(http)
    example.collect(http)  # same hour: overwrite, never duplicate

    with Session(engine) as s:
        assert s.scalar(select(func.count()).select_from(Item)) == 3
        assert s.scalar(select(func.count()).select_from(Signal)) == 6  # 3 posts x (likes, replies)
        assert {r.status for r in s.scalars(select(ConnectorRun))} == {"ok"}
    assert len(seen) == 4  # 2 pages x 2 runs


def test_bad_key_fails_fast_without_retrying():
    seen = []
    http = httpx.Client(base_url=example.API, transport=httpx.MockTransport(
        lambda req: seen.append(req) or httpx.Response(401, json={"error": "bad key"})))

    with pytest.raises(httpx.HTTPStatusError):
        example.collect(http)

    assert len(seen) == 1  # a 4xx is never retried
    with Session(engine) as s:
        assert s.scalars(select(ConnectorRun.status)).one() == "error"


def test_schema_change_fails_the_run_instead_of_loading_bad_rows():
    http, _ = fake_api([[{"id": "p1"}]])  # upstream dropped fields

    with pytest.raises(ValidationError):
        example.collect(http)

    with Session(engine) as s:
        assert s.scalar(select(func.count()).select_from(Item)) == 0
        assert s.scalars(select(ConnectorRun.status)).one() == "error"

7

Register it in dbt metric catalog + freshness

Required: every metric the connector writes must be in the metric catalog. If one is missing, the not_null_stg_signals_kind test fails and the whole dbt build stops. That's on purpose: it's the contract between ingestion and transform.

dbt/seeds/metric_catalog.csv: one row per metric (kind = cumulative | gauge | per_period) 
example,likes,cumulative,hour,Total likes of a post
example,replies,cumulative,hour,Total replies to a post
dbt/models/staging/_sources.yml: a freshness check for the source 
      - name: example_signals
        identifier: signals
        config:
          loaded_at_field: captured_at
          freshness:
            warn_after: {count: 2, period: hour}
            error_after: {count: 6, period: hour}
            filter: "source = 'example'"

No metrics (like RSS)? Check the job instead: identifier: connector_runs, loaded_at_field: finished_at, filter on the source and status in ('ok', 'partial'). A source-specific staging model is only needed if the source needs its own cleaning; stg_items and stg_signals already cover every source.

terminal 
cd dbt && uv run dbt build --profiles-dir . && uv run dbt source freshness --profiles-dir .

5 · Special cases (with an existing example to copy)

Most sources differ from the template in one way. Each pattern already exists in the code.

Login / token

Session token that expires

Cache the token in a module-level dict; on 401, clear it and retry once. Copy twitch.py (_token, _headers). Bluesky works this way.

Quota API

Daily unit budget

Charge each call to run.quota_used and commit before calling; stop at a threshold. Copy youtube.py (_call, quota_used_today).

Upstream not ready

Resource doesn't exist yet

Set run.status, run.error = "waiting", "…" and return. It isn't an error and won't alert. Copy twitch.collect.

Late data

Values arrive late or get revised

Re-fetch a lookback window every run; the upsert overwrites corrections. Copy wikipedia.collect (30 days).

No metrics

Records without numbers (RSS)

Write items only. Don't invent a "mentions = 1" signal at ingest; count mentions per hour in dbt from published_at.

Not JSON

XML feeds

Bronze is JSONB: store {"url": …, "entries": [...]} with the parsed entries. Store titles, links and times only, never article text.

Strict rate limit

One request every N seconds

Space requests out in the loop and keep pages few. If errors come back as HTTP 200 with text, the pydantic contract fails the run, which is what you want.

Missing items

404 for one item isn't a failure

Return None from _get, log a warning, continue. Copy wikipedia._get.

7 · Common mistakes

Key in the URL (?key=…)
Header or POST body. httpx logs every URL.
Exact fetch time as captured_at
this_hour() or a date. Otherwise every run adds rows.
One commit at the end of the run
Commit per page, so a crash keeps what was fetched.
Retrying 401 / 403 / 404
@retry_http already retries only 429, 5xx and network errors.
Inventing metrics at ingest
Store what the API gives; derive counts in dbt.
Storing article text or personal data
Titles, links, public names, counts only.
Forgetting the compose env line
Without it the worker sees no key and silently skips the job (only a warning in the logs).
Trusting any HTTP 200
Let the pydantic contract decide. A 200 with an error text must fail.
